## Test manuel Google Calendar / Apple Calendar (procédure documentée — à rejouer par Vibe Work avec captures)

Le fichier de preuve généré pendant la mission est un export réel de 5 événements (voir ci-dessus). Procédure :

1. **Google Calendar** (calendar.google.com, compte de test) → ⚙️ « Paramètres » → « Importer » → sélectionner `centeryou-export.ics` → calendrier cible « Personnel » → « Importer ». Vérifier : aucun message d'erreur ; les 5 événements apparaissent aux bonnes dates/heures **dans le fuseau local du compte Google** (heures flottantes) ; la journée entière apparaît bien en « toute la journée » ; la récurrence hebdomadaire de « Réunion équipe » apparaît chaque semaine le mardi ; la catégorie est lisible dans la description.
2. **Apple Calendrier** (macOS ou iCloud.com, compte de test) → Fichier → « Importer… » (macOS) ou « Nouveau calendrier d'événements » puis glisser le fichier (iCloud) → vérifier idem : pas d'erreur, 5 événements, all-day correct, récurrence affichée.
3. **Re-aller-retour** : dans Google/Apple, ré-exporter ce calendrier en .ics, puis l'importer dans Centeryou (Réglages → Agendas → Importer) → aperçu « 5 événements détectés » (les doublons exacts sont ignorés si la coche est laissée) → compte-rendu 5 importés / 0 refusé.

Côté code, la compatibilité est prouvée structurellement (validation RFC 5545 ci-dessus + round-trip + tests) : le fichier exporté suit exactement les conventions produites par Google/Apple (CRLF, pliage 75 o, flottant, VALUE=DATE, RRULE FREQ seul).

## Décisions importantes

- **Heures flottantes à l'export** (mission) : aucun `Z` ni `TZID` ajouté — l'app reste en heure murale locale, point fort audité ; à l'import, une valeur `Z` est convertie en heure locale de l'appareil, un `TZID` est ignoré avec une note (jamais silencieusement faux).
- **All-day = 00:00→00:00** dans l'app (convention « 00:00 = minuit de fin de journée ») ↔ `VALUE=DATE` + DTEND exclusif dans le fichier. Fin « 00:00 » exportée le lendemain à 00:00 pour garder une durée positive côté .ics, et réimportée correctement.
- **Événement traversant minuit refusé** avec un message honnête (« Centeryou ne représente pas encore les événements de nuit ») — l'app ne sait pas encore les représenter (audit Sentinelle, axe 2), aucun jargon.
- **RRULE bornées (COUNT/UNTIL) ou INTERVAL>1 matérialisées** en occurrences `repeat: 'jamais'` (plafond 366, note dans le compte-rendu) : l'app n'a pas de notion d'intervalle/borne, matérialiser est la seule représentation fidèle. RRULE simple intervalle 1 → répétition native, ce qui rend le **round-trip export→import identique**.
- **Doublon = titre + date + début + fin identiques** (énoncé mission), testé contre le store existant ET entre événements du même fichier ; coche « ignorer les doublons » cochée par défaut.
- **Import = ajout uniquement** via `store.importEvents` (sanitize item par item avant le store) ; la restauration de sauvegarde, elle, continue de remplacer après confirmation explicite — inchangé.
- **Plafond 1 Mo** sur le fichier (taille en octets du `File.size`), message FR avec la taille réelle ; titres tronqués à 140 caractères (alignement `maxLength` des champs de saisie, point noté par l'audit) avec note dans le compte-rendu.
- **Chunk lazy** : `await import('../../lib/ics')` uniquement dans les gestionnaires de clic (pattern Cloche) — preuve : chunk 595 non référencé par le HTML initial de `/`.
- **Le test en date de Cloche** (`rappels.test.ts`, `TODAY='2026-11-20'`) échoue sur `main` depuis le 2026-11-21 UTC — pré-existant, non modifié, signalé dans la PR.
